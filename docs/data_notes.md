# 数据说明：Solomon VRPTW 标准算例集

本文记录流水线对输入数据校验出的结论，以及上游文件内部不一致的两处问题。两处问题都可以用本文给出的命令在本仓库中复现。

## 来源与完整性

| 项目 | 内容 |
|---|---|
| 来源 | <https://github.com/PyVRP/Instances>，目录 `VRPTW/Solomon` |
| 许可 | MIT（见 `LICENSE` 中的算例数据声明） |
| 内容 | 56 个算例 × （`<name>.vrp`, `<name>.sol`）= 112 个文件，约 170 KiB |
| 获取方式 | `python scripts/fetch_solomon.py` |
| 完整性 | 逐文件 SHA-256 记录于 `data/raw/solomon/PROVENANCE.json`，可用 `python scripts/fetch_solomon.py --verify` 复核 |

算例分三个族：`C1`/`C2`（聚集分布）、`R1`/`R2`（随机分布）、`RC1`/`RC2`（混合分布）。每个算例均为 100 个客户，车队上限 25 辆。系列 1 的车场时间跨度短、时间窗紧（载重 200），系列 2 的时间跨度长、时间窗宽（载重 700–1000）。

## 流水线确认无误的部分（硬性校验，共 1120 项，0 错误）

* 每个算例声明的 `DIMENSION` 与 `NODE_COORD_SECTION`、`DEMAND_SECTION`、`TIME_WINDOW_SECTION` 的实际行数完全一致；
* 有且仅有一个车场，其需求与服务时间均为 0；
* 所有节点满足 `ready <= due`，且每个客户都能在其自身时间窗内从车场到达；
* 每个客户的需求都不超过单车载重，声明的车队总量足以承运总需求；
* 每个参考解都**恰好服务每个客户一次**，且用车数不超过声明的车队上限。

## 缺陷一：声明的成本与随文件附带的路径对不上

**56 个算例全部存在此问题**：声明的 `Cost` 与其自带路径的实际成本不一致。

```
C101   重算 828.9369   声明 827.3000   偏差 +1.6369
C201   重算 591.5566   声明 589.1000   偏差 +2.4566
R101   重算 1642.8769  声明 1637.7000  偏差 +5.1769
R104   重算 976.6932   声明 971.5000   偏差 +5.1932
```

重算值总是*更高*，高出 1.6 至 5.2 个距离单位（0.2%–0.5%），从不更低。这说明声明值是一个质量更好的公开最优解，而随文件附带的路径是一个略有不同的近似最优解。

C101 可以彻底确定我们采用的距离约定是否正确，因为这个算例存在广为流传的标准解文本。随文件附带的路径是

```
Route #1: 5 3 7 8 10 11 9 6 4 2 1 75
...
Cost 827.3
```

而公开流传的 C101 标准解在路径列表中遗漏了客户 75（一个存在已久的笔误），并声明 `Cost 828.94`。用不带取整的精确欧氏距离计算随文件附带的路径，得到 **828.9369**，即与标准解的 `828.94` 在其打印精度内一致——前提是客户 75 存在且位置正确：在客户 75 全部 100 个可能的插入位置中，文件所给的位置正是成本最低的可行位置。因此我们的距离度量是正确的，`827.3` 是另一个（更优的）解的目标值。

## 缺陷二：8 个参考解违反时间窗

**56 个参考解中有 8 个**包含一条在用精确欧氏距离计算时会晚于客户最晚服务时间的路径：

```
R102  route#18  客户 14：到达 42.07 > 最晚 42.00
R105  route#2   客户 83：到达 64.10 > 最晚 64.00
R107  route#1   客户 74：到达 169.14 > 最晚 169.00
R108  route#8   客户 28：到达 213.37 > 最晚 213.00
R112  route#8   客户 5： 到达 167.40 > 最晚 167.00
R211  route#3   客户 94：到达 656.34 > 最晚 656.00
RC101 route#4   客户 46：到达 143.07 > 最晚 143.00
RC105 route#1   客户 6： 到达 123.10 > 最晚 123.00
```

所有超出量都不到 0.4 个时间单位，正是 100 客户路径上累积的舍入误差量级；而且全部是*时间窗*超出：没有任何一条路径超出车辆载重。可见这些公开路径是在与精确欧氏距离略有不同的距离或时间精度下校验的。

## 流水线如何处理这些缺陷

每个校验项都带一个严重级别：

* `error`（错误）——校验失败意味着本流水线自身的解析、校验或输入处理有问题。这类失败会让程序以非零码退出。
* `advisory`（提示）——校验失败记录的是上游本就存在的不一致。这类问题连同完整证据一并报告、单独计数，绝不会导致流程失败。

`ref_cost_matches_declared` 与 `ref_routes_feasible_strict` 属于提示级，其余均为错误级。求解器始终使用严格容差（`uavvrp.vrptw.EPS = 1e-9`）；只有校验公开文件时才使用 `REFERENCE_TOLERANCE = 0.5`，且求解器的任何代码路径都无法接触到这个较松的容差。

对基准比较的影响，直说如下：

* **与文献比较时**：应使用声明值一列（`ref_cost_published`）作为公开最优解。不要指望求解器能在这份数据上复现它，也不要把随文件附带的路径当作最优参考——它们的成本最多高出 5.2。
* **与自己跑的基线比较时**：应使用 `ref_cost_recomputed`，即随文件附带路径的实际成本，因为双方用的是同一个度量。

两个数值都写在 `data/processed/manifest.csv` 与 `data/processed/validation_report.json` 中。

## 如何复现这些结论

```bash
python scripts/fetch_solomon.py --verify     # 校验输入数据完整性
python scripts/run_preprocess.py             # 1120 项校验，0 错误，56 条提示
```

控制台摘要会打印前几条提示；逐算例的完整列表（含精确到达时间）在 `data/processed/validation_report.json` 中。
